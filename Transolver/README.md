# Warped-IFW Transolver Directory Guide

## Overview

This directory implements a **Transolver autoregressive point-cloud pipeline** in **JAX** for the **Warped-IFW** dataset.

At a high level, the code does the following:

1. Loads raw `.npz` CFD-style samples.
2. Converts raw arrays into pointwise supervised learning samples.
3. Splits the dataset by geometry so train and test geometries are disjoint.
4. Optionally crops meshes by distance to the airfoil and caches preprocessing.
5. Optionally subsamples meshes using uniform, biased, or reconstruction-validated strategies.
6. Normalises positions, input velocities, distance-to-surface, and targets using training-set statistics.
7. Trains a Transolver-style autoregressive model directly on irregular point clouds.
8. Uses a teacher-forcing schedule during training and pure autoregressive rollout during evaluation.
9. Computes subsampled and full-mesh metrics, component losses, and per-sample reports.
10. Saves checkpoints, final model artifacts, predictions, metrics, and visual diagnostics.

This guide explains the **directory structure**, the **purpose of each script**, the **data flow**, and the **main implementation ideas** needed to understand and work with the project.

---

## What problem this code solves

Each raw dataset sample contains:

- point positions in 3D,
- a set of airfoil/surface point indices,
- a history of input velocities,
- future output velocities,
- pressure values over time.

The goal of the Transolver pipeline is to learn an autoregressive mapping:

$$
\text{past velocity history + geometric context} \rightarrow \text{future velocity rollout}
$$

More concretely:

- **Input per point**: 5 past velocity frames, flattened into 15 channels, plus distance-to-surface, for a total of 16 channels.
- **Model prediction step**: one future velocity frame at a time, with 3 output channels.
- **Rollout horizon**: 5 future frames.
- **Training mode**: autoregressive rollout with a teacher-forcing schedule and weighted per-step loss.
- **Operating domain**: irregular point clouds, without rasterising to a fixed voxel grid.

Unlike the FNO pipeline, this model operates **directly on irregular meshes / point clouds** and therefore has to deal explicitly with varying point counts, optional cropping, and subsampling policies.

## End-to-end pipeline summary

The pipeline can be understood in seven stages.

### 1. Raw data loading and sample construction

Handled by `load_data.py`.

Raw `.npz` files are converted into a common pointwise format:

- `x`: point positions, shape `(N, 3)`
- `fx`: pointwise inputs, shape `(N, 16)`
- `y`: pointwise rollout targets, shape `(N, 15)`
- `idcs_airfoil`: indices of airfoil points

### 2. Geometry-disjoint train/test split

Also handled by `load_data.py`.

Files are grouped by geometry ID parsed from the filename. Entire geometries are assigned either to train or test so there is no geometry leakage.

### 3. Optional preprocessing: cropping and caching

Handled by `preprocessing.py`.

Samples can be cropped by distance to the airfoil so that only points within a configurable radius are kept. This reduces point count before training and can focus the model on near-body flow regions.

### 4. Optional subsampling for efficient training/evaluation

Handled by `subsampling.py`.

Because full meshes can be large, training and validation can operate on subsets of points. The code supports:

- uniform subsampling,
- biased subsampling toward near-wall / high-variance regions,
- reconstruction-validated subsampling.

### 5. Normalisation

Handled by `normalisation.py`.

The code fits separate training-set statistics for:

- positions,
- velocity-history columns,
- distance-to-surface,
- targets.

This separation is important because these feature groups have different physical scales.

### 6. Autoregressive model training

Handled mainly by `train.py`, using `loss.py` and `checkpoint.py`.

The model predicts one frame at a time, updates the input window, and rolls forward for 5 output steps. Teacher forcing is used during training according to a schedule, but evaluation is done with pure rollout.

### 7. Evaluation, saving, and visualisation

Handled by `evaluate.py`, `checkpoint.py`, and `visualise.py`.

The pipeline can:

- run full autoregressive inference on full meshes,
- denormalise predictions,
- compute dataset metrics,
- export per-sample CSVs,
- save final model artifacts,
- generate 2D/3D figures, animations, MATLAB bundles, and diagnostic reports.

# Core data representations

Understanding the project is easiest if you first understand the sample structure and tensor shapes.

## Raw dataset sample

Each `.npz` file contains:

- `t`: shape `(10,)`
- `pos`: shape `(100000, 3)`
- `idcs_airfoil`: shape `(20000,)`
- `pressure`: shape `(10, 100000)`
- `velocity_in`: shape `(5, 100000, 3)`
- `velocity_out`: shape `(5, 100000, 3)`

Interpretation:

- There are `100000` points in the 3D domain.
- There are 5 input time steps and 5 output time steps.
- Each velocity frame is 3D: $$u_x, u_y, u_z$$.

## Converted Transolver sample

Produced by `build_transolver_sample()` in `load_data.py`.

### `x`

```python
x.shape == (N, 3)
```

Point coordinates.

### `fx`

```python
fx.shape == (N, 16)
```

Features per point:

- channels `0..14`: flattened 5-step input velocity history,
- channel `15`: distance to nearest airfoil / surface point.

The velocity flattening is:

```text
[v_t0(3), v_t1(3), v_t2(3), v_t3(3), v_t4(3)]
```

So each point gets:

$$
5 \times 3 = 15
$$

velocity values, plus one distance feature.

### `y`

```python
y.shape == (N, 15)
```

Target future velocities, flattened as:

```text
[v_t5(3), v_t6(3), v_t7(3), v_t8(3), v_t9(3)]
```

### `idcs_airfoil`

Local indices of airfoil points within the current sample.

---

## Autoregressive interpretation of `fx` and `y`

Although `y` stores all 5 future frames flattened together, the model conceptually does:

$$
[v_{t0}, v_{t1}, v_{t2}, v_{t3}, v_{t4}] \rightarrow v_{t5}
$$

then

$$
[v_{t1}, v_{t2}, v_{t3}, v_{t4}, \hat{v}_{t5}] \rightarrow \hat{v}_{t6}
$$

and repeats until all 5 future frames are generated.

So the model is trained as a **single-step predictor** but used as a **5-step autoregressive rollout model**.

# How geometry-disjoint splitting works

The split is implemented in `load_data.py`.

## Filename convention

The code expects filenames of the form:

```text
{geometry_id}_{case_id}-{window}.npz
```

using:

```python
FILENAME_RE = re.compile(r"^(?P<geometry_id>[^_]+)_(?P<case_id>[^-]+)-(?P<window>\d+)$")
```

Only `geometry_id` is used for train/test splitting.

## Grouping by geometry

All files are grouped by geometry ID, then the geometry IDs are shuffled with a fixed seed.

## Assigning test geometries

The number of test geometries is approximately:

$$
\max(1, \operatorname{round}(|G| \cdot \text{test\_frac}))
$$

where $$G$$ is the set of unique geometry IDs.

Then:

- some geometries are assigned to `test`,
- the rest are assigned to `train`.

All files from a chosen geometry go entirely into one split.

## Why this matters

This prevents leakage across:

- different time windows of the same geometry,
- different cases on the same geometry,
- different files that still share the same shape.

So the model is evaluated on **unseen geometries**, not merely unseen files.

Responsible for:

Loads one `.npz` file into a dictionary of NumPy arrays.

- `x`
- `fx`
- `y`

#### `subsample_sample_uniform(...)`

Simple uniform subsampling helper that can preserve all airfoil points.

#### `load_split(...)`

Full convenience entry point:

1. list files,
2. split by geometry,
3. load train and test raw samples,
4. convert them to Transolver samples.

This dataclass controls almost all behaviour in the pipeline, including:

- no-slip handling,
- cropping,

- evaluation frequency,

Two predefined profiles are provided:

## `preprocessing.py`

### Purpose

Provides mesh preprocessing utilities, mainly for **distance-based cropping** and optional caching.

### Main idea

Large meshes can be reduced before training by retaining only points within some distance of the airfoil.

### Key functions

#### `sample_cache_key(sample, suffix="")`

Builds a hash key based on point coordinates and airfoil indices, useful for caching.

#### `_compute_distance_to_airfoil(...)`

Recomputes per-point distance to the airfoil if no distance feature is present.

#### `get_distance_column(sample, ...)`

Retrieves the distance column from `fx`, or recomputes it if needed.

#### `reindex_airfoil_after_mask(mask, idcs_airfoil)`

When points are removed, airfoil indices need to be remapped to the new local indexing.

#### `apply_mask_to_sample(sample, mask)`

Applies a boolean mask consistently to `x`, `fx`, `y`, and `idcs_airfoil`.

#### `crop_sample_by_distance(sample, max_dist, ...)`

Keeps only points with distance less than `max_dist` and returns both the cropped sample and crop statistics.

#### `preprocess_samples(samples, cfg, split_name, cache_dir=None)`

Main preprocessing entry point. For each sample:

- optionally crops by distance,
- records before/after sizes,
- optionally caches the processed sample list to disk.

### Why preprocessing matters

Cropping reduces memory and compute, especially if the downstream flow field far from the airfoil is less important than near-body behaviour.

## `subsampling.py`

### Purpose

Implements more advanced point subsampling strategies used during training and validation.

This is important because the Transolver model works directly on point sets, and full meshes may be too expensive for every training step.

### Supported modes

#### 1. `uniform`

Randomly sample points, optionally preserving all airfoil points.

#### 2. `biased`

Samples points with higher probability if they are:

- close to the wall,
- or in regions where the velocity history has higher temporal variance.

This biases training toward more dynamically important regions.

#### 3. `recon`

A more expensive mode that:

1. proposes biased subsets,
2. reconstructs the full target field from the subset using k-nearest-neighbour interpolation,
3. measures reconstruction error,
4. accepts a subset if the error is below a threshold.

This tries to ensure the chosen subset still preserves enough information to approximate the original sample well.

### Key functions

#### `_variance_score_from_fx(sample)`

Computes a variance-based score from the input velocity history.

#### `_biased_weights(sample, cfg)`

Builds sampling weights by combining:

- inverse distance to airfoil,
- local velocity-variance score.

#### `_select_indices_uniform(...)`

Uniform subset selection.

#### `_select_indices_biased(...)`

Biased subset selection.

#### `_apply_indices(sample, idx)`

Returns a new subsampled sample with remapped airfoil indices.

#### `_reconstruct_from_subset(source_sample, subset_sample, k=4)`

Reconstructs a full target field from a subset using inverse-distance weighting over nearest neighbours.

#### `_relative_recon_error(...)`

Measures relative reconstruction error over selected rollout frames.

#### `subsample_sample(...)`

Public entry point that dispatches to the selected mode and optionally uses memory/disk caches.

### Important implementation note

The code explicitly fixes an earlier logic issue where the `recon` branch was unreachable due to unconditional returns in earlier branches.

## `normalisation.py`

### Purpose

Fits and applies feature normalisation.

### Why separate normalisation is used

The code normalises these groups independently:

- positions `x`,
- velocity columns in `fx[:, :15]`,
- distance column `fx[:, 15]`,
- targets `y`.

This is important because position coordinates, velocities, and distances can have very different scales. Mixing them into one shared normalisation can distort the effective representation.

### Key functions

#### `fit_pos_stats(train_samples)`

Fits mean/std for coordinates.

#### `fit_vel_stats(train_samples)`

Fits mean/std for input velocity-history columns.

#### `fit_dist_stats(train_samples)`

Fits mean/std for distance-to-airfoil.

#### `fit_y_stats(train_samples)`

Fits mean/std for targets.

#### `apply_normalisation(...)`

Applies all four normalisations and rebuilds `fx` with separately normalised velocity and distance columns.

#### `fit_and_apply(train_samples, test_samples)`

Fits stats on the train set only, then applies them to both train and test samples.

#### `denormalise_y(y_norm, y_stats)`

Converts predictions back to original target units.

## `loss.py`

### Purpose

Defines rollout losses used during training.

### Key functions

#### `build_step_weights(n_steps, gamma=1.0, supervised=())`

Builds a normalised per-step weight vector.

If `supervised_steps` is empty, all rollout steps contribute. Otherwise only selected steps are weighted nonzero.

This allows pushforward-style training or nonuniform emphasis on later rollout steps.

#### `relative_l2_step(pred, target, mask=None)`

Relative $$L_2$$ loss for one step, with NaN/Inf guards.

#### `rollout_loss(preds, targets, step_weights, mask=None)`

Weighted sum of per-step relative $$L_2$$ losses over the rollout.

#### `mae_rollout(preds, targets, mask=None)`

Mean absolute error over the rollout.

#### `divergence_penalty(v, pos, k=6)`

Optional geometric regulariser based on local velocity divergence estimated through nearest neighbours.

### Important implementation feature

The loss code is defensive against non-finite values. If one step becomes non-finite, the whole parameter tree is not contaminated by NaNs.

## `train.py`

### Purpose

Main training script for the Transolver autoregressive model.

It ties together:

- data loading,
- preprocessing,
- normalisation,
- model construction,
- subsampled training,
- teacher forcing,
- evaluation,
- checkpointing,
- final artifact export.

### Model construction

#### `build_model(cfg)`

Creates a `TransolverCore` using a `TransolverCoreConfig` built from `RunConfig`.

The core model is imported from:

```python
from model.core import TransolverCore, TransolverCoreConfig
```

### Learning-rate schedule

#### `make_schedule(cfg, steps_per_epoch)`

Uses:

- linear warmup,
- then cosine decay,
- with a floor learning rate.

### Teacher forcing

#### `monotone_tf_steps(epoch, cfg)`

Computes how many rollout steps still use ground-truth history at a given epoch.

#### `build_tf_mask(k)`

Builds a length-5 mask where the first `k` steps use teacher forcing.

### Input helpers

#### `split_fx(fx)`

Converts flattened input history back to `(N, 5, 3)` plus distance.

#### `apply_noslip(v, idcs)`

Forces airfoil velocities to zero.

#### `loss_point_mask(...)`

Can optionally exclude airfoil points from the training loss.

### Data augmentation

#### `augment_sample(sample, rng, cfg)`

Supports:

- flipping the `y` axis,
- positional noise,
- velocity noise,
- optionally leaving airfoil points unchanged.

### Training loop structure

The `train(...)` function runs several nested workflows each epoch.

#### 1. Gradient-update pass

For each train sample:

- augment sample,
- subsample to `cfg.train_points`,
- split input history,
- run autoregressive rollout with teacher forcing,
- compute weighted rollout loss,
- update parameters with Optax.

#### 2. Honest train loss pass

A deterministic subset of train samples is evaluated with **no teacher forcing**. This gives the logged `train_loss`.

#### 3. Test loss pass

Test samples are also evaluated with **pure rollout**, again no teacher forcing.

This makes train/test losses comparable.

#### 4. Component breakdown

Per-component losses are computed for both train and test subsets.

#### 5. Optional periodic full-mesh evaluation

Every `cfg.full_eval_every` epochs, the code performs full-mesh inference on test samples using `predict_dataset(...)`, then computes point-level full-mesh metrics.

#### 6. Checkpointing

Every `cfg.save_checkpoint_every` epochs, a checkpoint is saved.

### NaN recovery and monitoring

This training loop has several robustness features:

- per-element and global gradient clipping,
- detection of non-finite loss,
- detection of NaNs in parameters,
- restoration of the last known-good parameters,
- tracking of gradient norms,
- NaN counts logged per epoch.

### Fine-tuning stage

After the main training stage, the code can optionally run `cfg.finetune_epochs` additional epochs, often with reduced or zero subsampling.

### `main()` workflow

The main script does the following:

1. parse CLI args,
2. build config,
3. seed NumPy,
4. create run directory,
5. optionally start W&B,
6. load train/test data,
7. optionally truncate number of files,
8. preprocess train and test samples,
9. normalise them,
10. build the model,
11. train the model,
12. run final full-mesh evaluation,
13. save final artifacts,
14. optionally write config to a user-specified path.

# How the model learns across different geometries

The model does **not** learn one separate network per airfoil.

Instead, it learns one shared mapping:

$$
\text{geometry-aware flow history} \rightarrow \text{future flow}
$$

across many geometries at once.

Geometry is encoded implicitly through:

- point coordinates,
- distance-to-surface,
- the spatial arrangement of the input velocity history,
- which points belong to the airfoil.

During training, the same parameters are updated using samples from many geometries. This lets the model learn reusable physical patterns such as:

- near-wall flow evolution,
- wake development,
- relationships between surface proximity and velocity change,
- temporal propagation of local flow structures.

Because the split is geometry-disjoint, test-time performance measures how well that learned operator transfers to unseen geometries.

# Training and inference flow in one picture

A good mental model is:

```text
raw .npz
  -> load_data.py builds point samples
  -> preprocess_samples() optionally crops
  -> fit_and_apply() normalises train/test
  -> train.py subsamples per step
  -> model predicts one frame ahead autoregressively
  -> loss.py computes weighted rollout loss
  -> checkpoint.py saves run state
  -> evaluate.py predicts full test set and computes metrics
  -> visualise.py builds plots / animations / reports
```

# Practical notes and caveats

## 1. Variable point counts are normal

Because cropping and subsampling can change node counts, many saved arrays are ragged object arrays rather than fixed dense tensors.

## 2. Full-mesh eval is the important final metric

The subsampled train/test losses logged every epoch are useful for monitoring, but the most realistic final evaluation is the full-mesh autoregressive rollout.

## 3. Teacher forcing is only for training

Logged train/test loss uses pure rollout with no teacher forcing. This is a good design choice because it measures the actual deployed behaviour of the autoregressive model.

## 4. Hard no-slip is enforced explicitly

If enabled, predicted velocity is zeroed on airfoil points both during rollout and after denormalisation.

## 5. Reconstruction-based subsampling is more expensive

`recon` mode improves subset quality but adds subset-search and reconstruction overhead.

# Final takeaway

This Transolver directory implements a **geometry-aware autoregressive point-cloud forecasting pipeline** for CFD-style velocity rollout.

Its main distinguishing features are:

- direct operation on irregular point clouds,
- geometry-disjoint evaluation,
- optional cropping and advanced subsampling,
- separate normalisation of position / velocity / distance / targets,
- teacher-forced training with pure-rollout evaluation,
- strong support for checkpointing, diagnostics, and visual analysis.

If you understand:

- the sample format `x`, `fx`, `y`, `idcs_airfoil`,
- how preprocessing and subsampling change point sets,
- how autoregressive rollout is trained and evaluated,
- and how artifacts are saved and reloaded,

then you understand the core of this Transolver project.
